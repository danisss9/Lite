# Full HTML5 conformance plan

Planning baseline: 12 October 2026 (refreshed from 3 October with the measured progress below). Scope: Windows x64, screen rendering, retaining Lite's C#/AngleSharp/QuickJS/Skia architecture. This document is an implementation plan; it does not change the active compatibility profile or claim that any new coverage has passed. The current state and confirmed-gap inventory live in [html5-conformance.md](html5-conformance.md); this document defines the order of work and the rules that keep each gate honest while it grows.

## Target and completion contract

Keep the [W3C HTML5 Recommendation of 28 October 2014](https://www.w3.org/TR/2014/REC-html5-20141028/) (HTML 5.0) as the normative target. The WHATWG living standard, HTML 5.1 and later W3C editions are not targets; where a pinned WPT test asserts later behavior, the later assertion is classified `post-target`, not silently absorbed. Modern features that exist in Lite as extensions (details/dialog, picture, modules, and other regressions from later targets) stay available but never count as HTML 5.0 requirements.

Browser chrome, OS accessibility platform mappings, and HTTP/TLS internals retain their published profile exclusions. Everything HTML-visible â€” including sandbox, origins, prompt APIs, and obsolete-element processing â€” remains required. Dependency specifications (DOM, Web IDL, URL, Encoding, MIME, Fetch, Unicode/Bidi, Web Storage, Web Messaging, workers, File API) are mapped per clause as dependencies; they are tracked where HTML 5.0 references them and are not auto-inherited as whole workstreams.

Completion means every applicable user-agent obligation is inventoried from the pinned Recommendation, implemented, and supported by identity-matched passing evidence. It does not mean a selected manifest is green. `html5ProfileReady` must remain false until the section review and the evidence collection are complete; passing regressions and a green gate never establish readiness by themselves.

## Milestone 1: applicability review and gate growth (closed 5 November — inventory complete under the guarded check)

Review the catalog against the pinned Recommendation, root by root, and grow the executable gate. Proposed batch order â€” smallest, most-dependable roots first so the review protocol hardens before the large `html` root: `dom`, `uievents`, `url`, `encoding`, `webstorage`, `webmessaging`, `cookies`, `fetch`/`cors` (dependency-mapped), `FileAPI`, `selection`, `mimesniff`, then `html` by subdirectory (syntax/parsing, semantics, browsers, editing, forms, interaction, rendering, infrastructure, dom/documentsâ€¦).

Classification protocol (schema-constrained to `path`, `classification`, `reason`, plus assertion inventories for `mixed`):

- `included` â€” every subtest is a 2014-target obligation and passes. Included tests are the gate; they must pass in the same change that includes them.
- `mixed` â€” the file mixes 2014-target and later-era assertions. Requires `assertionInventoryComplete` with a per-assertion classification and reason; the gate tolerates failure only in reviewed non-target assertions.
- `post-target` â€” the assertions only bind behavior introduced after HTML 5.0 (for example `toggleAttribute`, `append`/`prepend`, `replaceChildren`, `moveBefore`, lazy loading, `customElements`). A one-line normative justification naming the later feature is required.
- `regression-only` â€” curated Lite regression or a later-target regression fixture that cannot count toward HTML 5.0 readiness.
- `profile-excluded` â€” the obligation itself is outside the compatibility profile (chrome, accessibility mappings, networking internals).
- `unreviewed` â€” everything else, including a **reviewed applicable test that Lite currently fails**: record `reason: "Reviewed (failing): <spec clause, failing assertion, engine gap>"` so the review is preserved in text while the machine state stays out of the gate. Each such entry is added to the Milestone 4 work queue and becomes `included` only when it passes. Never include a failing test to show work, and never use an exclusion classification to hide an applicable failure.

Gate growth discipline: each batch is classified, then `--suite html5` must exit 0 before the batch is considered done; `inventoryComplete` flips to true only when every catalog candidate has a classification, and omissions are detected from the catalog rather than trusted from the flag.

Progress at the baseline: the `dom` root is reviewed (45 `included`, 1 `mixed`, 93 `post-target`, 23 `regression-only`; the 24 remaining `unreviewed` entries all carry reviewed reasons â€” 20 reviewed-failing feeding the Milestone 4 queue and 4 reviewed-deferred whose embedded post-target member reads cannot be split at subtest level), the first `mixed` assertion inventory is complete, and two entries were reclassified `post-target` against the 2014 REC's own text on re-review. Remaining: the dependency roots in the batch order above and the entire `html` root.

**Exit:** a reviewed corpus of meaningful size across the dependency roots, zero unexpected failures, the reviewed-failing queue feeding Milestone 4, and the review protocol demonstrated end to end on the `dom` root.

### Validation cadence (when runs resume)

The commands below are the cadence for the stages above; this planning pass executed none of them. Every subsequent engine or harness change rebuilds first and reruns the gates its cluster touches (the parse/tokenizer gates after parser or tokenizer edits, `--suite html5` plus the cluster after engine packages, the profile verdict at each checkpoint), because the evidence identity fingerprints source, profile, lock, binaries, checkout and manifest. Use `dotnet build Lite.sln -c Release` and the custom executable runner `dotnet run --project Lite.Tests -c Release --no-build` for code validation, then:

```powershell
./scripts/fetch-tests.ps1 -IncludeCss21Official

dotnet run --project Lite.Conformance -c Release --no-build -- --suite html5-inventory

```
