# Vendored AngleSharp

This project builds the pinned upstream AngleSharp parser from source so the HTML 5.0
conformance track can carry tree-construction patches the NuGet package does not have.

## Provenance

- Upstream: https://github.com/AngleSharp/AngleSharp
- Base: tag `v1.7.3`, commit `0e6979a` (matches the NuGet package pinned in
  `Directory.Packages.props` at 1.7.3; verified by assembly identity: name `AngleSharp`,
  version `1.7.3.0`, public key token `e83494dcdc6d31ea` from upstream's committed
  `Key.snk`, which this project signs with).
- Scope: `src/AngleSharp/**` only (no upstream tests, benchmarks or docs). The upstream
  project file is replaced by `Lite.AngleSharp.csproj`, which keeps the upstream compile
  surface for net8.0 (`Nullable` enable, LangVersion latest, SYSLIB0014 suppressed).

## Patch policy

The `native/src` tree starts pristine. Every deviation from upstream is a git commit on
top of it and MUST be listed here with the html5lib/WPT evidence that motivates it, so
the diff against the pinned tag stays reviewable (`git diff v1.7.3-equivalent`).
Re-basing onto a newer upstream tag is a deliberate, separately-reviewed act.

| Patch | Motivation |
| --- | --- |
| 001 — menuitem parses as a normal element (`HtmlMenuItemElement` loses `Special\|SelfClosing`; `menuitem` removed from the `AllBodyClosed` void-close list) | menuitem is absent from the W3C HTML 5.0 REC, so its start tag takes the "any other start tag" path and accepts children; upstream's post-2014 void semantics hoisted content out as siblings. menuitem-element.dat 9→18/20 (two residuals: formatting reconstruction with `<p><b></p><menuitem>`, and the in-select case whose expectation is itself post-2014). |
| 002 — foreign-content breakout applies in the fragment case (`ForeignNormalTag` no longer branches to `ForeignSpecialTag` when `IsFragmentCase`; the pop loop checks before popping, and the fragment-root case reprocesses through the insertion-mode rules via `Home` to avoid re-dispatching on the foreign context) | REC §8.2.5 pops breakout tags out of foreign content with no document/fragment distinction; upstream disabled the breakout for fragments, so `<nobr>`, `<div>`, `<h1>`, … inside an SVG/MathML fragment context stayed foreign (`<svg nobr>`, `<math div>`). foreign-fragment.dat 48→64/66. |
| 003 — fragment context tokenizer states are HTML-namespace only (`ParseFragment` gates the RCDATA/RAWTEXT/… setup on `context.NamespaceUri == HTML`) | The context-element tokenizer state list names HTML elements; an SVG `<title>` fragment context is foreign content parsed in the data state with integration-point rules. Upstream matched on the local name alone, so SVG title fragments parsed their input as RCDATA text (`foreign-fragment.dat` svg title/svg desc cases). |
| 004 — input/keygen/textarea in select: close-select + reprocess, with the fragment context counting for the scope check | The 2014 in-select rule pops until a select is popped, resets, and reprocesses; upstream's version ignored the tokens entirely in fragments (the context select is not on the stack). webkit02 #43 (document, sibling) and tests_innerHTML_1 #76/77 (fragment, root children) both hold under this reading; tests7 #33's nested-keygen expectation contradicts the 2014 letter and the sibling expectation of #43 — recorded as a corpus-internal inconsistency. |
| 005 — the data state emits U+0000 as-is; HTML text insertion drops it (`HtmlTokenizer.DataText` appends NUL; `AddCharacters` strips it — `Foreign()` already replaced NUL with U+FFFD) | §8.2.5 replaces NUL with U+FFFD in foreign text; upstream's tokenizer dropped NUL before the tree builder ever saw it, so `<svg>\u0000filler` lost both replacement characters (plain-text-unsafe.dat #14/#15 now pass). Four plain-text-unsafe cases (#1/#2/#4/#5) flip the other way: their expectations ignore NUL during the head phases — post-2014 behavior the 2014-correct engine no longer reproduces (recorded for the expectation-invalid family). |
| 006 — template in after-head processes using the in-head rules against the existing head | Browsers insert `<template>` into head in the after-head mode; upstream fell through to the anything-else branch, creating a body and landing the template there. Not yet effective on the corpus (template.dat #103–105 still fail) — needs a follow-up trace. |
| 007 — frameset mode inserts every whitespace character and ignores the rest (`InFrameset` filters per character instead of `TrimStart` + reprocess) | The in-frameset whitespace rule keeps each space/tab/LF/FF; upstream's TrimStart dropped all but one space (`<frameset> te st\n` dumps `"  \n"` in browsers). tests2.dat #7 fixed; #6's two-space run still differs. |
| 009 — NUL replacement in foreign text does not clear frameset-ok; other non-whitespace characters do (`Foreign`'s character case computes the flag per character) | Chromium keeps the frameset for `<svg>NUL</svg><frameset>` and `<svg>NUL </svg><frameset>` but drops it for `<svg>NULa</svg><frameset>`: the replacement character inserts without touching the flag, while any other non-whitespace character clears it. Upstream cleared for the NUL too, burying the frameset under the body. plain-text-unsafe.dat #18/#19/#20. |
| 008 — the reset's html case follows the head pointer (`Reset()` selects before-head when the document has no head, otherwise after-head, instead of upstream's unconditional before-head) | The 2014 reset algorithm: "If the head element pointer is null, switch the insertion mode to before head; otherwise, the head element pointer is not null, switch the insertion mode to after head." The after-head EOF then synthesizes the body. Upstream's before-head surfaced once the template-in-after-head handling left the stack as [html] at the `</template>` reset: EOF created a second empty head AND a body (template.dat #103-105 — the corpus wants one head carrying the template plus the synthesized body, matching Chromium). |
| 009 — NUL replacement in foreign text does not clear frameset-ok; other non-whitespace characters do (`Foreign`'s character case computes the flag per character) | Chromium keeps the frameset for `<svg>NUL</svg><frameset>` and `<svg>NUL </svg><frameset>` but drops it for `<svg>NULa</svg><frameset>`: the replacement character inserts without touching the flag, while any other non-whitespace character clears it. Upstream cleared for the NUL too, burying the frameset under the body. plain-text-unsafe.dat #18/#19/#20. |
| 010 — tokens at HTML/MathML text integration points process with the in-body rules, except in-body-ignored start tags while a table is in table scope (`Consume` routes integration-point tokens to `InBody`; `AllNested` start tags fall through to the mode rules when `IsInTableScope(Table)`) | The integration-point rule processes tokens with the in-body insertion-mode rules regardless of the current mode; upstream dispatched by mode, so a `<tr>` token reaching a `<mo>` integration point inside a foreign fragment re-entered the table modes and inserted a stray `<tr>` at the fragment root (math.dat/svg.dat #1-4, tests9/tests10 — all 8/8 after the patch). The table-scope exception matches Chromium, which inserts the second `<td>` of `<table><tr><td><svg><desc><td>` as a sibling cell through the table rules (tables01/webkit01/pending-spec-changes stay green). End tags keep the mode path: routing `</desc>` through the in-body end-tag rules left integration points unclosable. |
| 011 — CSS type selectors match HTML elements case-insensitively and every other element case-sensitively (`TypeSelector.Match` picks `Isi` for `IHtmlElement`, ordinal otherwise) | CSS 2.1 §4.1.3: element selectors are case-sensitive unless the document language says otherwise — HTML does, XML does not. Upstream compared case-insensitively unconditionally, so `DIV { color: red }` matched a lowercase `<div>` in an XML-parsed XHTML document (case-sensitive-007). HTML-served documents keep the insensitive path; the vendored CSS package's parser produces these selectors. |
| 012 — the "in select" anything-else rules ignore every remaining start and end tag unconditionally (`InSelect` drops the button-insert, xmp-to-in-body, insert-when-current-isn't-select and close-on-name-match branches) | REC §8.2.5.4.15 "in select": anything else (start and end tags) is "Parse error. Ignore the token." Upstream inserted unknown/button/xmp start tags whenever the current node was not the select, and closed same-named end tags, so `<select><option><hr>` grew an hr inside the option and `</p>`-style tags could pop elements. webkit02.dat #18/#26-47, tests9.dat #5/#17/#18, tests10.dat #4/#16/#17 now match the letter; the corpus's insert-happy trees (and its customizable-select button/selectedcontent cases #38/#40/#41/#44-47) are expectation-invalid for the pinned 2014 target and move to the reviewed ledger. |
| 013 — the in-cell cell-end pop runs until an *HTML* td/th has been popped (`InCellEndTagCell` walks the stack itself instead of `ClearStackBackTo(AllTableCells)` + one close) | REC §8.2.5.4.14 "in cell": "Pop elements from the stack of open elements until an HTML element whose tag name is td or th has been popped." The name-only clear stopped at the SVG `<td>` inside a foreignObject — a foreign element is never the target — so `</td>` left svg-td/foreignObject/span open and the following characters sank into the foreign subtree instead of fostering out of the table. namespace-sensitivity.dat #0 fixed. |
| 014 — the after-frameset character rule filters whitespace per character (`AfterFrameset` inserts only the space/tab/LF/FF of the run and drops the rest) | REC §8.2.5.4.20 "after frameset": whitespace characters insert, anything else is ignored — per character, so a mixed run keeps its inner space. Upstream TrimStart'ed the run (inserting only the leading whitespace) and dropped the remainder wholesale, losing the second space of `</frameset> te st`. tests2.dat #7 fixed. |
| 015 — numeric character references accumulate in 64 bits and overflow follows the out-of-range rule (`GetNumericCharacterReference` sums into a `long`; above U+10FFFF raises the invalid-number error and emits U+FFFD) | The 2014 tokenizer consumes digits without bound; the 32-bit accumulation wrapped wide references onto small code points (`&#x100000041;` became "A" instead of U+FFFD). numericEntities.test #38–41 and test4.test #38–41 (33/65-bit hex and decimal entities). |
| 016 — the comment-end NUL rule appends two dashes and the replacement character (`CommentEnd`'s NUL case appends `--\uFFFD`, not `-\uFFFD`) | The comment-end state's NUL rule appends two hyphens plus U+FFFD before switching back to the comment state; upstream appended one dash, so `<!----\u0000` emitted `-\uFFFD` instead of `--\uFFFD`. test3.dat #179. |
| 017 — an unopened DOCTYPE system identifier stays missing (`DoctypeSystem`/`DoctypeSystemIdentifierBefore` no longer flush the empty buffer into `SystemIdentifier` on `>`/EOF) | The before-doctype-system-identifier end/EOF rules raise (missing-doctype-system-identifier / eof-in-doctype), force quirks and emit with the identifier *absent*; upstream flushed the empty buffer into the token, manufacturing `SYSTEM ""`. The PUBLIC mirror never had the assignment — the asymmetry is why only SYSTEM cases failed. test3.dat #502–508, #622, #901–907, #1019. |
| 018 — an empty named character reference rewinds its terminator (`GetLookupCharacterReference` backs up when the scan consumed no name characters; the error check still sees the terminator) | The character after `&` that is not a name character was read but never consumed, and the data loop's next read skipped over it: `&;` emitted `&` and lost the semicolon. The rewind restores the read position so the terminator is reprocessed as text; `&unknown;`-style references are unaffected (their trim loop already rewinds). test2.dat #21. |
| 019 — the CDATA-section state raises its EOF parse error (`CharacterData` raises EOF at end of input; the text is still emitted) | The 2014 CDATA section state ends at EOF with a parse error (the corpus's `eof-in-cdata`); upstream emitted the text silently. Error-occurrence only — no token changes. The 52 CDATA-EOF tokenizer runs. |

One known engine limitation stays unpatched because the fix outweighs the corpus: a
literal U+FFFF in the input stream is indistinguishable from the tokenizer's end-of-file
sentinel (`Symbols.EndOfFile = Char.MaxValue`), so the engine replaces it with U+FFFD
(unicodeChars.test #61). Fixing it means reworking the EOF discipline across the whole
char-stream layer; the tree-construction corpus never carries a raw U+FFFF.

## Coordination

AngleSharp.Css and AngleSharp.Xml stay on their NuGet pins; both bind the vendored
assembly by its unchanged strong-name identity. The CSS 2.1 track compiles against the
